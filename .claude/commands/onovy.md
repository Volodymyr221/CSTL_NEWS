## Крок 3 — Оновити пульс `CSTL NEWS VOVA/NOW.md`

```
node scripts/now_update.mjs
```

Це перепише **тільки** авто-блок (гілка · останній коміт · `CACHE_NAME` · останній
PR · стенди · що не доїхало в `main` · чи є журнал · статус потоку).

Далі **руками** переписати прозу — git цього не знає:

- 🎯 **ЗАРАЗ** — над чим працюємо цієї хвилини (один абзац);
- ✅ **ЗРОБЛЕНО В ЦІЙ СЕСІЇ** — з журналу, з номерами PR і деплоїв;
- 🚧 **НЕ ДОРОБЛЕНО** — почате й покинуте, **обовʼязково з причиною**;
- ❓ **ВІДКРИТІ ПИТАННЯ ДО ВОВИ** — на що чекаємо відповіді;
- ➡️ **ДАЛІ** — черга великих задач (звірити з `BACKLOG_VOVA` / `AUDIT`);
- 🛑 **НЕ ЧІПАТИ** — крихкі місця.

🛑 **Жодної заглушки.** Порожній розділ гірший за відсутній — він виглядає як
відповідь. Сторож це ловить.

## Крок 5 — Перевірити

```
node tests/docs-fresh.mjs                      # свіжість входу + бюджет вікна
node tests/docs-refs.mjs                       # посилання не биті
node scripts/now_update.mjs --check --strict    # 🔴 СТРОГА звірка пульсу з git
```

🔑 **`--strict` тут не випадково.** Щоденна звірка (у `npm test`) навмисно мʼяка:
не чіпає хеші комітів і список «що не доїхало в `main`», бо ті біжать з кожним
комітом — а сторож, який червоніє після кожного коміту, перестають читати.
**Але на передачі саме ці поля й важать:** наступний чат читає їх як правду про
те, де лежить робота. Тому тут звіряється все до рядка.

🛑 Порядок має значення: спершу **закомітити** (Крок 6), потім прогнати `--strict`
ще раз і, якщо він червоний, оновити пульс і **долити коміт**. Інакше пульс
опише стан «до останнього коміту».

Змінювався код — ще й:
```
node --check <кожен змінений .js>
npm test
```

Червоне — **виправити, не передавати**. Передана поломка гірша за непередану роботу.

## Крок 8 — 🔴 Розвилка: зливати в `main` чи ні

Це єдине місце, де `/onovy` зупиняється й питає. Різниця принципова:

```
git diff --stat origin/main..HEAD -- index.html sw.js src/ style/ scripts/
```

**Порожньо (змінювались лише документи)** → зливай самому: PR + squash-merge.
Публікація сайту від документів не змінюється, а другий акаунт побачить усе
одразу в `main`, без полювання по гілках.

**Не порожньо (є код)** → 🛑 **СТОП.** Злиття в `main` = **деплой на живий сайт**.
Не зливай без слова Вови. Скажи прямо:

> «На гілці є код: `<перелік файлів>`. Злиття = деплой. Документацію оновив і
> запушив — другий акаунт її вже бачить на гілці `<назва>`. Кажи «деплой», якщо
> публікуємо, або лишаю на гілці.»

## Крок 9 — Звіт Вові: що НЕ доробили

Останнє і найважливіше. **Голосно, не дрібним шрифтом:**

```
📦 ПЕРЕДАЧА ГОТОВА — <дата, час>

Гілка: <назва>   ·   у main: <так / ні, чекає слова «деплой»>
Пульс NOW.md оновлено · журнал дописано · сторожі зелені

✅ Зроблено: <перелік з номерами PR/деплоїв>
🚧 НЕ доробили: <перелік з причинами>
❓ Чекаю відповіді: <питання>
➡️ Наступний крок: <що логічно робити далі>
```

Новий чат почне з `/startuem`, прочитає `NOW.md` **першим** і побачить рівно це.

## Чим `/onovy` відрізняється від `/finish`

| | `/onovy` | `/finish` |
|---|---|---|
| мета | **передати наступному чату/акаунту** | **опублікувати на сайті** |
| `NOW.md` | 🔴 головний результат | оновлює (Крок 4.1) |
| злиття в `main` | лише якщо самі документи | завжди (це і є публікація) |
| `CACHE_NAME` | не чіпає (документи на кеш не впливають) | піднімає, якщо змінювався код |
| підсумок для brain | ні | так (Крок 8) |

Обидві можна робити поспіль: спершу `/onovy` (передача), потім `/finish` (публікація).
