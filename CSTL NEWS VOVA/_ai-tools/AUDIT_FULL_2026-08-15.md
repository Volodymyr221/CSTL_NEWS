## 1. P0 / P1 — ЗНАЙДЕНЕ, З ДОКАЗОМ

### P1-1. 🔴 Повторне відстеження рейсу зберігає СТАРІ дані і СТАРІ прапорці «вже надіслано»

**Файл:** `src/core/supabase.js:1387` (`savePushSubscription`) ·
схема `scripts/supabase_push_schema.sql:37`.

```js
const r = await netCall(() => supa.from('push_subscriptions').insert(payload));
if (r.ok) return { ok: true };
if (r.rawError?.code === '23505') return { ok: true };   // ← «вже є» видається за успіх
```

Унікальний ключ — `(endpoint, route_id, track_date)`, тобто **без зупинок**.
Коментар у самій схемі обіцяє: «При повторному відстеженні — **upsert** оновлює дані
(dep_time, зупинки)». Код робить `insert`. Тобто намір задокументовано, а виконання
немає.

**Сценарій:** відстежив рейс ОЛИКА→ЛУЦЬК → отримав «за 15 хв» (`notified_warning = true`)
→ скасував → відстежив ТОЙ САМИЙ рейс того ж дня з іншої зупинки.
**Наслідок:** у базі лишається старий сегмент і `notified_warning = true` →
попередження **не прийде взагалі**, а якщо прийде — назве чужу зупинку.
**Фікс:** `.upsert(payload, { onConflict: 'endpoint,route_id,track_date' })` + скидання
`notified_*` у `false` при повторній підписці.

### P1-2. 🔴 Скасування відстеження з другого пристрою не скасовує push

**Файли:** `src/tabs/buses.js:141` (`unsubscribeFromPush`) ·
`src/core/supabase.js:1399` (`deletePushSubscription`) · `buses.js:244` (`hydrateTrackedFromDB`).

Гідрація тягне рейси **по `user_uuid`** (усі пристрої акаунта), а видалення
фільтрує **по `endpoint` цього пристрою**:

```js
.delete().eq('endpoint', endpoint).eq('route_id', routeId).eq('track_date', trackDate)
```

**Сценарій:** відстежив рейс на телефоні → відкрив застосунок на планшеті (рейс
підтягнувся гідрацією) → натиснув «скасувати» на планшеті.
**Наслідок:** DELETE не зачіпає жодного рядка (endpoint інший), але повертає успіх;
інтерфейс каже «скасовано», **push однаково прилітає на телефон**, а наступний вхід
на планшет `hydrateTrackedFromDB()` **повертає рейс у список**. Це рівно
«contradictory state» і «після перезапуску tracking повертається».
**Фікс:** видаляти по `user_uuid + route_id + track_date` (RLS це дозволяє —
`push_delete USING user_uuid = auth.uid()`), а не по endpoint.

### P1-3. 🔴 Перегони «увімкнув → одразу вимкнув»: підписка лишається висіти

**Файл:** `src/tabs/buses.js:1609-1674` (обробник `.bs-track-btn`).

Кнопка нічим не блокується на час запиту. `subscribeToPush()` асинхронний
(дозвіл → `pushManager.subscribe` → INSERT). Другий тап одразу викликає
`unsubscribeFromPush()` → DELETE може виконатись **раніше**, ніж дійде INSERT.
**Наслідок:** рядок у базі лишається після скасування → сповіщення про рейс, який
людина скасувала. Це те саме, що Вова описав як «push приходить через старий
subscription».
**Фікс:** блокувати кнопку на час операції (`aria-busy` + `disabled`) і серіалізувати
підписку/скасування на рейс (черга по ключу `routeId|date`).

### P1-4. 🔴 Немає `pushsubscriptionchange` — підписка вмирає мовчки

**Файл:** `sw.js` (обробника немає в усьому файлі).

Браузери періодично ротують push-підписку (втрата ключів, оновлення застосунку,
очищення). Без обробника рядок у базі лишається зі старим endpoint; при відправленні
сервер отримає `410` і **видалить його** (`send-bus-push:131`). Далі — тиша: людина
вважає, що відстежує рейс, а сповіщення не прийде **жодного**.
Частково рятує `selfHealPushSubscriptions()` — але лише для автобусів, лише при
відкритті вкладки Автобуси і **лише якщо дозвіл уже `granted`**; для чату,
коментарів і сторінок самолікування немає взагалі.
**Фікс:** обробник `pushsubscriptionchange` у `sw.js`, який переносить усі рядки зі
старого endpoint на новий.

### P1-5. 🔴 Відповідь на ПИТАННЯ не породжує жодного сповіщення

**Доказ:** тригери push стоять лише на `page_comments` і `page_posts`
(`scripts/supabase_comment_push.sql`, `supabase_page_push.sql`) і на приватних
повідомленнях. Питання — це `posts.type='chat'`, відповіді — таблиця `comments`.
**Жодного тригера на `comments` немає.**

**Наслідок:** ключовий цикл вкладки («запитав громаду → тобі відповіли») **розірваний**.
Людина мусить сама повертатись і перевіряти. Для продукту, який позиціюється як
соцмережа, це найбільша функціональна діра з усіх знайдених.
⚠️ Інфраструктура для доставки вже є: deep-link `#/post/disc/<id>` працює
(`app.js:373`, `board.js:2766`), пристрої лежать у `user_push_devices`.

### P1-6. 🔴 Заставка тримає екран 4.1 секунди **безумовно**

**Файл:** `src/app.js:473-479`.

```js
setTimeout(() => { splash.style.opacity = '0'; … setTimeout(() => { splash.remove(); … }, 600); }, 3500);
```

Час не залежить ні від чого: дані можуть приїхати за 200 мс — застосунок однаково
стоятиме зачиненим 4.1 с. **Кожен** запуск, **кожного** дня. У продуктах-орієнтирах
(Instagram, Telegram) заставка тримається рівно доти, доки не готовий перший екран.
⚠️ Складність: на цю затримку тепер **навмисно спираються** deep-link'и
(`core/splash.js`, `whenSplashGone()`), тож зменшувати час можна лише разом із ними —
але саме тому це і треба робити акуратно, а не «поміняти 3500 на 800».

### P1-7. 🟠 Deep-link на видалений обʼєкт = тиша

**Файл:** `src/tabs/board.js:2769` — `if (!post) return;`

Тап по сповіщенню про оголошення, якого вже немає → застосунок відкривається на
Громаді, **нічого не відбувається і нічого не сказано**. Вова назвав цей клас прямо:
«Push → tap → referenced object deleted».
**Фікс:** тост «Оголошення більше немає» + лишитись на Дошці. Те саме для
`focusFeedPost` (`feed.js:751`) і `openArticleById` (`news.js:217`).

### P2-4. Розрив 2-12 хвилин у попередженнях автобуса
`send-bus-push:167` — вікно попередження `minsLeft ∈ [13,17]`. Хто ввімкнув
відстеження за 10 хв до відправлення, не отримає **нічого** аж до `T-0`
(`minsLeft ∈ [-3,1]`). Ступенів «5 хв» і «1 хв», про які питав Вова, не існує.
Пропущений рейс теж не обробляється — підписка просто висить до кінця дня.

### P2-5. Витік слухача при кожному відкритті сторінки каналу
`src/tabs/feed.js:2476` — усередині `openPageScreen()`:
`window.addEventListener('resize', () => { measure(); onTitle(); })` — анонімна
функція, `removeEventListener` немає ніде. Відкрив сторінку десять разів — десять
постійних слухачів, кожен читає розкладку. На iOS `resize` сипле від клавіатури й
адресного рядка, тобто шлях робочий, не теоретичний.
⚠️ Взірець у проєкті вже є: `board-chat.js` (`api._cleanup`) і `board-discussions.js`
(`_chatViewportHandler`) свої слухачі знімають правильно.

### P2-6. Подвійний тап по ♥ може розійтись із базою
`src/tabs/feed.js:1223` — `toggleLike()` не серіалізований. Два швидкі тапи шлють
`setPageReaction(on=true)` і `setPageReaction(on=false)` без гарантії порядку;
відкат при збої повертає стан, захоплений на початку ПЕРШОГО виклику. Екран показує
одне, база тримає інше — лайк «зникає» після перезавантаження.

### P2-7. Лист коментарів перемальовується цілком на кожен чужий коментар
`src/tabs/feed.js:1545` — `listEl.innerHTML = …`. Той самий клас вади, який 15.08
лікували в стрічці (`paintIfChanged`), у листі коментарів лишився.
✅ Приватний чат зроблено правильно — `insertAdjacentHTML('beforeend')`
(`board-chat.js:297-321`), тобто дописування, а не перебудова.

### P2-8. Заборона масштабування у `<meta viewport>`
`index.html:5` — `maximum-scale=1.0, user-scalable=no`. У встановленому PWA
(основний сценарій) це **фізично не дає збільшити текст** — WCAG 1.4.4.

## 3. ЩО ПЕРЕВІРЕНО І ВИЯВИЛОСЬ СПРАВНИМ

- **RLS `push_subscriptions`** — закрито правильно (`supabase_anon_lockdown.sql`),
  анонім не пише і не видаляє; знімок бази у `scripts/RLS_SNAPSHOT.md` збігається.
- **Автентифікація Edge Functions** — `send-bus-push` вимагає секрет із `app_secrets`
  плюс `verify_jwt`; публічний ключ як «захист» більше не використовується.
- **Теги push** — кожен тип має власний (`chat-<thread>`, `comment-post-<id>`,
  `page-<id>`), тобто розмови не затирають одна одну.
- **Черга незавершених скасувань** (`PENDING_UNSUB_KEY`) — продумана: переживає
  офлайн, не знімає свіжу підписку, протерміноване лишає серверу.
- **Кеш-стратегія `sw.js`** — network-first для коду й даних із `{cache:'reload'}`,
  cache-first лише для картинок; збій картинки віддає порожню відповідь, а не HTML.

## 4. ЩО ПЕРЕВІРИТИ НЕМОЖЛИВО В ЦІЙ СЕСІЇ

- **Жива база і cron.** MCP Supabase у цій сесії **не авторизований** — перевірити,
  чи справді працює `cron` на `send-bus-push`, скільки рядків у `push_subscriptions`
  і які політики стоять НАЖИВО, я не можу. Усі висновки по базі — з файлів схеми.
- **iPhone.** Chromium не відтворює клавіатуру iOS і поведінку PWA у standalone.
