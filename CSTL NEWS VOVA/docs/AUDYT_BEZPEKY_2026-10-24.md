## Як міряли

Методика скіла: знахідка «підтверджена» тільки тоді, коли є **хто** (менш довірена
людина) → **що подає** → **яка перевірка мала зупинити** → **яку межу перейшло** →
**що постраждало**. Решта — «перевірити» або «зміцнення» (не дірка, а запас міцності).
Бойовий сайт НЕ атакували — лише читали код, живі політики RLS (правила доступу
до рядків), права на колонки й тригери бази (SQL-читання), поради Supabase.

## Висновок

Каркас міцний: Service Worker (фоновий працівник) не кешує особисті відповіді;
Edge Functions (серверні функції) перевіряють, хто кличе; AI-агенти не мають shell
(командного рядка) і пишуть лише **чернетки** — публікує людина; секретів у репо
немає; більшість `innerHTML` (вставка HTML) екранована. Але знайдено **чотири
справжні дірки в базі** — всі одного класу: *«дозволено змінити рядок» без
«заборонено змінити ОЦІ колонки»* — і одну дірку XSS (підкидання скрипта) у
статтях з кабінету. До запуску з живими людьми їх треба закрити.

## 🟡 Зміцнення (не дірки, але дешево)

1. **`safeHref()`** — одна функція для всіх посилань від людей/агентів (`video-feed.js:62`, `home-fund.js`, `news.js` джерела, `saved-hub.js` `window.open`): лише `https:`/`http:`. Збори вже мають `CHECK url ~* '^https://'` у базі — там ок.
2. **`prune_digest_log`, `prune_push_quota_log`, `rollup_content_views`** викликаються анонімом через `/rpc` → `revoke execute … from public, anon, authenticated` (їх кличе лише cron).
3. **`community-photos`**: завантажити може будь-хто в будь-який шлях → `with check` на папку `auth.uid()` (для відео вже зроблено за `can_edit_page`).
4. **Вихід з акаунта** лишає в localStorage замовлення ринку, збережені статті, позначки чатів, геолокацію погоди → чистити ключі акаунта в `signOut` (`auth.js:578`).
5. **CSP** — почати з `Report-Only` (лише звітує, нічого не ламає) на `admin.html`, потім `index.html`.
6. **GitHub Actions** (автоматизація): `supabase/setup-cli` і `gitleaks-action` закріпити за SHA (хешем коміту), CLI — точна версія замість `latest`; додати `permissions: contents: read` у `db-backup`, `functions-deploy`, `gitleaks`, `tests`, `test-vopas`; входи `workflow_dispatch` (`mission`, `days`) передавати через `env:`, а не прямо в shell.
7. **Поради Supabase**: 3 view (подання) з SECURITY DEFINER (`posts_public`, `ads_public`, `page_reaction_counts`) — навмисні вітрини, але варто `security_invoker` там, де можливо; увімкнути захист від злитих паролів (Auth).
8. `admin.html:1622` — `r.status`/`r.kind` без `escapeHtml`; `market-page.js:530` — `rel="noopener"`.

## ✅ Перевірено й чисто

- Edge Functions: власник/автор звіряється з JWT; службові — спільний секрет; текст пушу складається з бази, не від того, хто кличе; SSRF (запит на чужу адресу) немає.
- `profiles`: людина НЕ може змінити `official`, `trusted`, `approved_count` (колонкові права).
- `posts`: оновлює лише адмін; подача — через `submit_board_post` з перевіркою входу.
- AI-агенти: лише `web_search`, вихід через `strip_html`, статус `draft`; prompt injection (підкинуті інструкції на сторінці) може дати хибний факт у чернетці — тому чернетку читає людина.
- Workflows: немає `pull_request_target`/`issue_comment`; секрети не друкуються.

## Порядок робіт (коли скаже «Роби»)

Б1 → Б2 → Б3 (одна міграція SQL, ~30 хв + стенд, що учасник НЕ може змінити
`post_id`/`sender_uid`/`official`) → Б5 (санітайзер + стенд з `onerror`) → Б4 →
зміцнення 2-3 → решта.
