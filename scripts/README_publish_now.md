# «Опублікував — вийшло одразу» (`publish-now`)

> Що це: кабінет після публікації **сам будить** воркфлов `cms-sync`, і стаття
> зʼявляється на сайті за хвилину-дві замість очікування розкладу.

---

## Навіщо це взагалі знадобилось

📐 **Заміряно через GitHub API 27-28.08.2026.** Розклад `cms-sync` просив **288
прогонів на добу** (`*/5`), а GitHub давав **три**: 27.08 о 05:07 і 16:27, 28.08
о 01:03. Тобто напис у кабінеті «стаття зʼявиться за ~5 хвилин» насправді означав
**8-11 годин**.
📉 І це погіршення, а не разовий збій: 18.08 той самий розклад заміряли по 30
прогонах — виходило приблизно раз на 33 хвилини.

🔑 **Опитувати чергу — не той інструмент.** Розклад у GitHub Actions працює «за
можливості», і найчастіші розклади відкидають першими. Тому 28.08 частоту знизили
до `*/15` (щоб обіцянка стала чесною), а швидкість дала **подія**: публікація
штовхає синк.

## Що вже зроблено (код у репозиторії)

| частина | де |
|---|---|
| Edge Function `publish-now` | `supabase/functions/publish-now/index.ts` — задеплоєна, `verify_jwt: true` |
| виклик із кабінету | `admin.html` → `publishArticle()` → `штовхнутиСинк()` |
| страховка №1 | `cms-sync.yml`, тригер **`push` у `main`** — синк будить кожне злиття (28.08) |
| страховка №2 | той самий воркфлов, розклад `7,22,37,52` — ненадійний, див. нижче |

🛑 **Гейт — та сама функція, що в RLS:** `has_editor_perm('publish')`, викликана
**від імені людини** (її JWT). Другої копії правила «кому можна публікувати» не
заводимо: дві копії одного правила в цьому проєкті вже розходились.
🛑 **Що саме можна розбудити — вписано в код** (`cms-sync.yml`, гілка `main`), а не
приймається з запиту. Інакше будь-хто з правом публікації міг би запустити
будь-який наш воркфлов — зокрема деплой чи бекап.

## 🔴 ЩО ЛИШИЛОСЬ ЗРОБИТИ ВОВІ (один раз, ~3 хвилини)

Функції потрібен токен GitHub. Створити його може **лише власник акаунта**.

**1. Створити токен**

```
github.com → Settings → Developer settings → Personal access tokens
          → Fine-grained tokens → Generate new token

Token name:            CSTL publish-now
Expiration:            365 days   (запиши дату — коли протермінується, кнопка
                                   просто перестане прискорювати, розклад лишиться)
Repository access:     Only select repositories → Volodymyr221/CSTL_NEWS
Repository permissions → Actions:  Read and write
```

⚠️ Більше **жодного** права не давати. Цей токен уміє рівно одне — запускати
воркфлови в одному репозиторії.

**2. Покласти токен у секрети Supabase**

```
supabase.com → проєкт «Olyka Castle» → Edge Functions → Secrets → Add new secret

Name:  GITHUB_DISPATCH_TOKEN
Value: <токен із кроку 1>
```

**3. Перевірити**

Опублікувати будь-яку статтю в кабінеті → відкрити
`github.com/Volodymyr221/CSTL_NEWS/actions` → прогін `CMS Sync` має зʼявитись
**одразу** з позначкою `workflow_dispatch` (а не `schedule`).

## Якщо щось не так

| що бачиш | що це означає |
|---|---|
| стаття вийшла не одразу, а на найближчому злитті в `main` | секрет не доданий або токен протермінувався. 🔑 Тепер кабінет каже це **вголос**: у тості буде дослівна причина від сервера (28.08) |
| у журналі `github 401` / `github 403` | токен недійсний або без права `Actions: Read and write` |
| у журналі `not allowed` | у людини немає права публікації (`has_editor_perm('publish')`) — це не збій, а гейт |

🔑 **Публікація НІКОЛИ не залежить від цієї функції.** У базі стаття вже позначена
`ready`, і її забере або найближче злиття в `main`, або розклад.

🔴 **28.08 — ЩО ЗМІНИЛОСЬ, І ЧОМУ ТОКЕН УЖЕ НЕ ТЕРМІНОВИЙ.**
📐 Заміряно того ж вечора: розклад мовчав **16+ годин**, і розведення хвилин не
дало нічого. Тому синк тепер будить **`push` у `main`** — подія, яку GitHub
доставляє надійно. Стаття виходить за **17 секунд** після злиття.
➡️ Токен потрібен рівно для одного випадку: **публікація вночі або на вихідних**,
коли в `main` ніхто нічого не зливає.
🛑 І ще одне: раніше кабінет мовчки ковтав помилку прискорення. Тепер він показує
**дослівну причину від сервера** — «прискорення, а не умова» більше не означає
«не кажемо про це людині».
