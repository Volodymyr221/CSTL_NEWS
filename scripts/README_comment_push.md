# Як увімкнути згадки і сповіщення про коментарі (для Вови)

> Клієнтська частина вже на сайті. Щоб запрацювали **згадка «Віктор,»** і **сповіщення**,
> треба зробити два кроки в Supabase. Обидва — руками, бо в тій сесії конектор Supabase
> не був авторизований.

---

## Крок 1 — накатати схему (2 хвилини)

1. Відкрий **Supabase → SQL Editor → New query**
2. Скопіюй туди **весь** вміст файлу `scripts/supabase_comment_push.sql`
3. Натисни **Run**

Має відпрацювати без помилок. Файл безпечно запускати повторно — нічого не зламає.

**Що перевірити після:**
```sql
-- 1. колонка зʼявилась
select column_name from information_schema.columns
 where table_name = 'page_comments' and column_name = 'reply_to_uid';

-- 2. тригер стоїть
select tgname from pg_trigger where tgname = 'trg_notify_new_page_comment';

-- 3. добіг у розкладі
select jobname, schedule from cron.job where jobname = 'flush-comment-push';
```
Усі три мають повернути по рядку.

> ⚠️ Якщо `create extension pg_cron` лається — увімкни розширення в
> **Database → Extensions → pg_cron**, тоді запусти файл ще раз.

---

## Крок 2 — задеплоїти функцію сповіщень

Функція лежить у `supabase/functions/send-comment-push/`.

**Через інтерфейс Supabase:** Edge Functions → Deploy new function → назва
**`send-comment-push`** → вставити вміст `index.ts`.

**Через термінал** (якщо стоїть Supabase CLI):
```
supabase functions deploy send-comment-push --no-verify-jwt
```

🔴 **`--no-verify-jwt` обовʼязково.** Функцію кличе сама база, у якої немає токена
людини — з увімкненою перевіркою вона відповідала б 401 і сповіщення не йшли б.
Функція захищає себе інакше: спільним секретом, який знає лише база.

---

## Як перевірити наживо

1. З другого акаунта відповісти на твій коментар → тобі має прийти
   **«Імʼя відповіло на ваш коментар»**, а в самій відповіді — **«Твоє Імʼя,»** бордовим
2. Тап по сповіщенню → відкриється той самий пост, лист коментарів, потрібний рядок
   підсвічений
3. Написати під твоїм дописом кілька коментарів поспіль → перше сповіщення одразу,
   далі 10 хвилин тиші, потім зведене **«Ще N коментарів під вашим дописом»**

**Якщо сповіщення не приходять:**
```sql
-- відповіді функції (200 = все добре, 401 = проблема з секретом)
select status_code, content from net._http_response order by created desc limit 5;

-- секрет узагалі є?
select name from app_secrets where name = 'page_push_secret';
```
Якщо секрету немає — створити один раз:
```sql
insert into app_secrets (name, value)
values ('page_push_secret', encode(gen_random_bytes(32), 'hex'))
on conflict (name) do nothing;
```

## Що буде до накатування

Нічого не зламається — але це не «саме по собі», а зроблено навмисно.

Код на сайті може випередити міграцію (він деплоїться пушем, а SQL накатуєш ти руками).
Якби ми просто читали й писали колонку `reply_to_uid`, то до накатування **зник би весь
список коментарів** і **перестала б працювати кнопка «Відповісти»** — база відповідала б
«немає такої колонки». Тому обидва запити спершу пробують із колонкою, а на цю конкретну
помилку повторюють без неї (перевірено тестом).

Тобто до накатування: гілка відповідей, «Ще N відповідей», лайки й самі відповіді
працюють як звичайно — просто немає згадки «Віктор,» і не йдуть сповіщення. Після
накатування все вмикається саме, без повторного деплою.
