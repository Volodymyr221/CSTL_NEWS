## 🔴 Найважливіше про безпеку

**Репозиторій публічний.** Дамп містить приватне листування жителів. Тому:

- архів **шифрується** до вивантаження, назовні йде тільки `.gpg`;
- **у репозиторій дамп не комітиться ніколи** — не додавай такий крок, навіть «тимчасово»;
- пароль шифрування знає лише GitHub Secret. **Загубиш пароль — усі бекапи мертві**,
  розшифрувати їх не зможе ніхто, включно з GitHub.

➡️ Збережи `BACKUP_PASSPHRASE` окремо від GitHub — у менеджері паролів.

---

## Крок 1 — створити два секрети (робиться один раз)

`github.com/Volodymyr221/CSTL_NEWS` → **Settings** → **Secrets and variables** →
**Actions** → **New repository secret**.

### Секрет 1: `SUPABASE_DB_URL`

Береться в Supabase: **Project Settings** → **Database** → **Connection string** →
вкладка **URI**, режим **Session pooler**.

⚠️ Саме **pooler**, а не «Direct connection». Пряме підключення Supabase віддає
тільки по IPv6, а сервери GitHub Actions ходять по IPv4 — з прямим рядком воркфлоу
не підключиться взагалі. Рядок pooler-а виглядає так:

```
postgresql://postgres.uabyfecseqnemvcqhdem:ПАРОЛЬ@aws-0-eu-central-1.pooler.supabase.com:5432/postgres
```

Замість `ПАРОЛЬ` — пароль бази (там же в Supabase, кнопка **Reset database password**,
якщо не пам'ятаєш).

### Секрет 2: `BACKUP_PASSPHRASE`

Просто довгий пароль, який ти вигадаєш. Ним шифрується архів. Не коротший за 20 символів.

## Крок 2 — перевірити, що працює

**Actions** → **DB Backup** → **Run workflow**. Через 2-4 хвилини внизу сторінки
запуску з'явиться артефакт `cstl-db-backup-РРРРММДД-ГГХХ`.

Далі бекап знімається сам щоночі о **04:00 за Києвом** і зберігається **14 днів**.

## Крок 3 — 🔴 ПЕРЕВІРКА ВІДНОВЛЕННЯ (не пропускати)

**Бекап, який жодного разу не розгортали, бекапом не рахується.** Половина зламаних
бекапів виявляються зламаними саме в ту хвилину, коли вони потрібні. Тому один раз
треба пройти шлях повністю.

### 3.1 Розпакувати

```
gpg --decrypt cstl-backup-РРРРММДД-ГГХХ.tar.gz.gpg > b.tar.gz
tar -xzf b.tar.gz
```

Має з'явитись: `roles.sql`, `schema.sql`, `data.sql`, тека `storage/`, `README.txt`.

### 3.2 Подивитись, що всередині справді дані

```
grep -c "COPY public.messages" data.sql
grep -c "CREATE POLICY" schema.sql
ls storage/ | wc -l
```

Перше число має бути ≥1 (є листування), друге — десятки (RLS-політики на місці),
третє — приблизно кількість фото.

### 3.3 Розгорнути в ОКРЕМИЙ проєкт

⚠️ **Ніколи не тренуйся на бойовій базі.** Створи в Supabase новий безкоштовний
проєкт (наприклад `cstl-restore-test`), візьми його рядок підключення і накоти
**в цьому порядку**:

```
psql "РЯДОК_ПІДКЛЮЧЕННЯ_ТЕСТОВОГО" -f roles.sql
psql "РЯДОК_ПІДКЛЮЧЕННЯ_ТЕСТОВОГО" -f schema.sql
psql "РЯДОК_ПІДКЛЮЧЕННЯ_ТЕСТОВОГО" -f data.sql
```

Порядок не випадковий: `data.sql` не ляже, поки немає таблиць зі `schema.sql`,
а частина об'єктів схеми належить ролям із `roles.sql`.

### 3.4 Звірити числа

```
psql "РЯДОК_ПІДКЛЮЧЕННЯ_ТЕСТОВОГО" -c "select
  (select count(*) from messages)      as повідомлення,
  (select count(*) from page_comments) as коментарі,
  (select count(*) from posts)         as оголошення,
  (select count(*) from profiles)      as профілі;"
```

Числа мають збігтися з бойовою базою. **Збіглися — бекап справжній.**
Після перевірки тестовий проєкт видали.

## Що цей бекап покриває, а що ні

**Покриває:** усі таблиці `public` (пости, коментарі, чати, оголошення, реакції,
профілі), RLS-політики, функції й тригери, акаунти (`auth.users`), файли бакета
`community-photos`.

**Не покриває:**
- **Edge Functions** — вони в репозиторії (`supabase/functions/`), тобто вже в git.
- **Налаштування консолі Supabase** — увімкнені провайдери входу, ліміти, Redirect URLs.
  Це кілька тумблерів; якщо колись розгортатимеш проєкт з нуля, їх треба виставити руками.
- **Секрети** (ключі, паролі) — і не має покривати.

## Якщо бекап впав

| Помилка у логах | Що це | Що робити |
|---|---|---|
| `Немає секретів: …` | не створені GitHub Secrets | Крок 1 вище |
| таймаут / `could not connect` | у секреті рядок Direct, а не pooler | взяти рядок **Session pooler** |
| `password authentication failed` | змінився пароль бази | оновити `SUPABASE_DB_URL` |
| `Не завантажилась більшість фото` | змінився шлях до сховища або бакет закрили | база в архіві ціла; розібратись зі сховищем окремо |
